## 范围与验收

## 当前证据

- 截图底部用户消息是浅灰气泡，没有明确发送失败提示；上方“已停止”属于较早的消息，不能直接判定为底部消息的状态。
- 对开发实例指定话题只读核查：最后两条用户请求分别为 interrupted 和 completed（总结）；总结之后未见新增收据或原文引用。但截图底部是否是旧的 interrupted 消息残留，还是相同正文的新发送，缺少手机 client_message_id，不能按正文判断，也不能断言这条灰色消息从未到达服务端。
- 使用运行版本的 HermesClient 经公网执行只读 capabilities、snapshot、sync、historyWindow：所有请求 HTTP 200，解析成功；最近历史的用户消息均有服务端消息身份和收据。此结果不是手机网络状态证明。
- App 的停止操作调用线程 stop，并不直接停止 MobileOutbox。截图本身不足以证明停止操作是根因。
- 当前无法远程读取手机 SecureStore 与内存中的 outbox 状态；必须用可执行回归证明确认的缺陷，不能把猜测标为手机根因。

## 状态转换核查与已证实缺陷

Jamie 补充触发条件是反复停止、发送。沿 nativeTransport → HermesClient → MobileOutbox → projectTimeline 检查：

- 停止按钮调用 `HermesClient.stop(threadId)` 的独立 HTTP 请求，不调用 `client.close()` 或 `MobileOutbox.stop()`；连接状态、发送确认、Agent 执行状态分别维护。
- SDK 对同一收据采用单向阶段更新，迟到的 running/queued 不覆盖 interrupted/completed；发送状态 accepted 表示权威接收，不等待执行完成。
- 新增 `stop-send-network.test.mjs` 使用实际 nativeTransport、SDK、outbox 和时间线投影，模拟 6 次停止/发送后再发送第 7 条；覆盖 running 收据迟到、一次接收确认丢失后同 ID 重试、断线重连与旧 socket 回调。原始 f48e5aa 和修复候选均通过：本实验**没有复现单纯反复停止导致状态混乱**，不能把通过归功于候选修复。
- 缺陷一：已保存权威接收确认后，下一条排队消息仍等待上一条历史请求结束才被唤醒。修正为持久确认落盘即唤醒下一条，不改变未确认消息的顺序与安全重试。
- 缺陷二：旧的已确认记录清理失败会设置全局 storageFault，永久停止后续发送。修正为仅该条清理保留并按已有轮询间隔重试；提交前保存失败或确认保存失败仍阻止不安全发送。
- 主控在独立临时基线副本运行两项定向测试：f48e5aa 两项均失败，候选通过。临时基线副本已清理，未覆盖工作树或主目录。
