# M1 网络可靠性：首版交付门槛

Jamie 要求网络通信保障和重试在首版完善，优先于继续扩展视觉功能。本文是验收要求和代码检查记录，不是功能完成报告。

## 默认自动处理，尽量不打扰用户

Jamie 明确要求通信恢复尽可能不打扰用户，不把技术判断交给用户。

- 断线、切网、暂时超时、确认丢失默认自动重连、查询收据、同ID原文安全重试和补齐；不能要求用户选择“重试还是放弃”、判断是否已接收或点击“重建同步”才能继续使用。
- 可恢复的临时故障使用轻量状态（如等待网络、正在恢复），不反复弹窗、不堆技术错误、不打断输入和阅读；恢复成功自动消退。手动重试只是可选快捷操作，不是必经步骤。
- 对可验证属于当前服务器/身份的过期同步游标，自动重建投影并保留待发记录及阅读位置；异常或身份不匹配游标不得静默跨身份使用。
- 执行结果不明时先自动核对权威收据与历史；无法确认时保留记录、明确状态，不自动创建新执行，也不要求用户猜测是否重跑。需要用户明确发起的全新执行不能冒充通信恢复。
- 只有无法自行恢复且确实需要用户动作时才提示，如令牌失效、权限被撤销或本地无法保存；说明具体原因和一个明确下一步，不给技术选项菜单，不隐瞒未发送/未完成状态。
- R4验收增加：正常网络故障恢复全程零必需点击、无决策弹窗，不需要用户理解收据/游标/幂等；确需介入的异常提示准确且不重复骚扰。

## 当前代码证据与缺口

- `apps/mobile/src/send.ts`：已有同ID原文手动重试及进程退出后将sending恢复为ambiguous；不能据此声称自动重试完整。
- `apps/mobile/src/App.tsx`：初始capabilities/catchUp失败进入catch后，不启动SDK连接循环；回前台catchUp失败也不会进入connect。网络恢复不能仅依靠这些入口自行保证。
- `packages/client/src/index.ts`：已有WS退避及catchUp，但connect启动后台循环即返回，不能把它作为连接成功证据；半开检测、超时、错误分类及退避重置边界需要专项测试。
- `App.tsx`：SecureStore的SEND_KEY只保存一条SendRecord；内存pendingRecords不等同持久队列，早先已接收但尚未结束的记录可能不再拥有独立本地恢复记录。按最小需求补齐，不假定需要无限离线队列。
- 已验证的最新历史窗口与用户消息receipt_id/client_message_id映射继续作为合并依据；禁止按相同正文去重。

## 必测故障窗口与预期

1. 接收前断网：本地消息可恢复，显示待发送/等待网络；恢复后安全提交。
2. 服务端已接收但ACK丢失：原ID原文重试只关联原收据，不新增消息或执行。
3. 执行中断线或切后台：服务端执行继续；回前台补齐状态，不重新提交任务。
4. 已完成但通知丢失：重连、冷启动均找回最终消息及终态，不能一直显示执行中。

上述窗口结合断网、弱网、Wi-Fi/蜂窝切换、后台、系统杀进程、服务重启、游标过期和多次点击重试验证；另测401/403、429/5xx、请求悬挂与WS半开。

- 网络错误与鉴权、协议、业务拒绝分开，不能无限重试全部错误。
- 区分本地保存、等待网络、提交结果不明、服务端已接收、执行中和终态；已接收不代表已完成。
- 自动重试针对可安全重放的请求；执行unknown不自动重新运行。停止/审批/频道创建等写操作不可套用无差别POST重试。
- 历史、状态与已读以服务端为准；客户端缓存仅用于恢复和展示；退出或换身份不能携带旧消息到新连接。
- 不要求iOS后台长期维持WS，也不以系统推送作为本轮前置；要求服务端执行与回前台恢复可靠。
