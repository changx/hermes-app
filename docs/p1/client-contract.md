# P1-05 shared client contract (03-backed)

Status: local integrated test clients, not a product UI or installed app. The pinned Hermes baseline is `2f16a1aa5a35feec496949abdef7ad51aea0e7ef`; protocol version is 1. Source of truth: [P1 protocol](protocol.md) and `plugins/hermes_app/adapter.py` in this worktree.

`packages/client/src/index.ts` is pure TypeScript with injected `HttpTransport`, `SocketFactory`, and a token provider. It imports no Node, Electron, DOM, React, or React Native modules. The caller owns secure credential storage and supplies the token at connection/request time; the client does not persist it. Every HTTP request and WS upgrade uses `Authorization: Bearer`; URL and logs never carry it. A browser native WebSocket cannot set the required header. `tests/client/desktop/transport.mjs` uses Node `ws` to prove the desktop JS target. `tests/client/mobile/transport.js` uses the React Native WebSocket options header; its Node execution uses a deliberate `ws` shim, not a phone runtime.

## Public operations

- `capabilities` requires protocol 1 with durable sync. Channel list/create/update/delete use `/v1/channels`; Thread list/create/get/update/archive use `/v1/channels/{id}/threads` and `/v1/threads/{id}`.
- `send(threadId, clientMessageId, text)` requires a caller-generated unique ID. A retry must repeat the same ID, Thread and exact text. A separate send, even with identical text, needs a new ID. The server returns a durable 202 receipt. `getReceipt` obtains queued, running, received, completed, failed, interrupted or unknown. Optional `admission:'followup'` identifies native busy input; `received` confirms only Gateway admission, never per-message model consumption or completion. Reaction is driven only by the optional nullable `processing` callback field: running → 👀, completed → ✅, failed → ❌, interrupted/null/omitted → none, unknown → ⚠️. `state`, `admission` and `handed_off` do not infer reaction. Callback results survive cold reads and terminal results cannot be cleared by late ACKs. See [native reactions](../m1-native-reactions.md). A normal fallback clears admission only with an exact core user anchor. Human-readable history retains each original followup in input/output order using its durable platform receipt and stable display ref. The native aggregated steer stays in model history and is not a second displayed input. Do not invent core row IDs or match text for identity. A received followup without its exact published client identity remains in the local outbox even after a successful history sync. SDK and mobile updates must accompany the server's new receipt state; older enum validators cannot consume it. Unknown is displayed for user resolution and never triggers an automatic new send or execution retry.
- `history` retrieves bounded pages of original visible refs; `historyAll` loads initial pages and message invalidations use `historyTail` after the last known ref. The map is merged by `ref_seq`, in order. A draft map is separate and is cleared on close. Missing original history and other non-2xx HTTP responses surface as errors. The existing SDK has not yet adopted the additive latest/older route below.
- `markRead` sends a visible ref and keeps the local ref monotone. The server remains authoritative for unread counts. Project lists are refetched after Channel invalidations; Thread metadata and read counts are refetched from the server after their events.
- Snapshot bootstraps bounded active/queued receipts and pending approval/clarify requests for a fresh device. Interaction events fetch their exact ID and remove settled/expired cards. Attachment events fetch metadata including explicit deleted/missing state. Message history carries attachment metadata only on the authoritative original USER row.
- History may contain a strict `role:'system', display_kind:'system_notice'` pair for durable memory/Skill review and compression notices. The SDK rejects either half without the other, merges edits by exact `ref_seq`, fences delayed history responses from replacing a newer edit, and never treats the row as assistant tool/Markdown output. Mobile renders it as compact plain system UI; it splits assistant continuation grouping on both sides while retaining normal scroll, unread and time behavior.
- `answerInteraction`, `stop`, `cancelQueued`, `upload`, `download`, `deleteUnattached`, and `search` call the P1-04 routes. Upload and download use injected binary transport methods; the shared module has no platform dependency. Send retries carry the same client ID, text and ordered attachment IDs.

## Additive server history/identity contract

`GET /v1/capabilities` retains protocol `1`, `history: true`, and existing keys, and adds `history_latest: true` and `message_send_identity: true`. On `GET /v1/threads/{id}/messages`, `limit` defaults to 50 and must be an integer from 1 to 100. Exactly one direction may be selected: no direction (original forward from start), `after=<next_cursor>` (original forward), `after_ref_seq=<visible ref_seq>` (forward tail), `latest=true` (most recent `limit` refs), or `before=<older_cursor>` (the preceding `limit` refs). Invalid combinations, foreign/wrong-direction/nonexistent cursors, and invalid limits return 400; an unknown Thread returns 404. Responses keep `messages` ascending by `ref_seq`, with `incomplete_turns` and `turn_outcomes`. `older_cursor` is an opaque, Thread-bound, backward-only cursor for the next preceding page, or `null` at the beginning; do not calculate offsets from global ref numbers. `next_cursor` remains the forward cursor after the last returned ref if newer refs exist, else `null`. For a latest page, use its last `ref_seq` with `after_ref_seq` to fetch new arrivals while paging older history with `older_cursor`; new arrivals cannot shift a preceding page. Existing forward pagination is unchanged apart from the additive `older_cursor: null` response key.

Each linked history USER message includes `receipt_id` and `client_message_id`; unlinked users and assistant messages omit both keys. Clients reconcile an optimistic send by exact identity, never by matching text. Normal turns and assistant output reference original SessionDB rows. Running followups additionally have durable platform-input refs backed by the already accepted receipt original, with opaque message ID `receipt:<receipt_id>`. These are display records, not fabricated core rows or proof of model consumption. Human-readable history uses the same stable `ref_seq` order for both sources; repeated sync and normal execution fallback must not insert a second input.

## Sync sequence

1. Take the first `/v1/snapshot` waterline and retain it while paging the remaining Thread summaries. Then fetch `/v1/channels`.
2. Replay `/v1/sync` from that first waterline. Process each event's referenced entity before advancing the cursor; a failed fetch leaves the last processed cursor intact. A 400 invalid/future/foreign cursor and a nonconsecutive event ID raise `ResyncRequired`. The caller explicitly invokes `resync` to obtain a new snapshot.
3. Open `/v1/events?cursor=<last processed>` through the injected authorized socket. WS event frames trigger serialized HTTP durable replay from the current cursor. Duplicate/old events do not create duplicate refs; entity version and event ID prevent stale fetch responses from replacing newer data.
4. On disconnect, replay HTTP first, then reopen WS with bounded backoff. `close()` aborts owned requests/socket and clears ephemeral drafts. It never calls a stop-execution route. Each `connect()` owns its controller, replay and socket; a completed run releases that ownership. After `ResyncRequired`, the caller can await `resync()` and call `connect()` again on the same client. A late close, handshake or HTTP reply from an aborted run cannot close a newer socket or advance its cursor. The caller should retain the last processed cursor in an identity-scoped cache if persistence is wanted; the SDK keeps it in memory only.

The WS factory buffers frames delivered between handshake and callback registration. The server holds durable state and original message text; the client maps are disposable views. No OpenAI/TUI JSON-RPC or Discord compatibility is involved. This remains a test SDK without a UI state store.

## Validation boundary

`bash scripts/client-check.sh BASELINE` type checks and runs injected transport/reducer tests. `node tests/client/real-gateway.mjs` runs the actual isolated plugin loader and GatewayRunner with a loopback synthetic model: desktop and mobile-shaped JS adapters authenticate, bootstrap a delayed approval, compete to answer, send and retry the same ID and attachments, cold-load history, download binary data, search, cancel, stop, mark read and replay after a process restart. In the one-command regression the child loads an unpacked plugin archive. Android Metro exports a JS bundle containing the shared module and native React Native view entry. The mobile network adapter executed in Node with a shim; no phone, APK, background OS behavior, credential vault, or installability is claimed.
