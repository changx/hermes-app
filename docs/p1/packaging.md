`bash scripts/pack-plugin.sh BASELINE` makes a reproducible gzip archive. The archive omits credentials, databases, tests, caches and build outputs. Compare with `sha256sum -c ARTIFACT.sha256`; inspect with `tar -tzf ARTIFACT`. After P1-04 merges, run this command again to produce a new content hash and verify new shipping files are included.

## Isolated install, disable, remove

These are instructions for a *disposable isolated* `$HERMES_HOME`, not the active Jamie profile. Stop its GatewayRunner before changing plugin files or restoring data. Check `git -C "$HERMES_BASELINE" rev-parse HEAD` against the SHA above and `sha256sum -c ARTIFACT.sha256`. Extract the archive under a temporary directory, inspect its `plugin.yaml`, then copy the `hermes-app` directory to `$HERMES_HOME/plugins/hermes-app`. Enable `hermes-app` in that isolated profile's `config.yaml` plugin and platform lists, supply a synthetic token through its private environment, and start the isolated runner. Verify `/v1/capabilities` reports protocol 1 before any migration. To disable, stop the runner, remove `hermes-app` from those two lists, restart and verify its listener is absent. To uninstall, stop the runner, make the backup below, then remove only `$HERMES_HOME/plugins/hermes-app`; preserve the profile data for recovery. Do not point these commands at an active profile.

## Coherent backup and restore

The core SessionDB (`state.db`) holds original text; plugin metadata (`hermes-app/metadata.sqlite`) holds Thread mappings, receipts, refs and sync events; Hermes ProjectDB (`projects.db`) holds Channel bodies. Attachments are currently absent from 03 but may be added by 04 under plugin-owned directories. A coherent snapshot must capture *all three databases plus the entire `hermes-app/` tree and any attachment directories as one stopped-profile set*. Do not back up one SQLite file while execution continues or copy metadata without SessionDB. A stopped-profile archive of the entire isolated `$HERMES_HOME` captures current and future plugin attachment directories and SQLite WAL/SHM siblings; store it in a private location because it can contain credentials and conversation text.

For migration, stop the isolated runner, take a complete private backup, record baseline/plugin hashes and schema versions, then stage the replacement plugin and start it against a copy of the backup first. Verify Channel/Thread list, historical refs, receipts and attachment reads before using the migrated copy. For rollback, stop the runner, restore the *whole* pre-migration `$HERMES_HOME` to a fresh isolated directory, restore the matching plugin archive and baseline, then start and verify the same data. Restoring only metadata or only SessionDB can produce false missing history or incorrect execution state. Never re-run an `unknown` receipt automatically; preserve it for explicit review. Active profile installation, deployment, signing and release need separate authorization.

For an isolated profile that is already stopped, an example private backup command is `tar -C "$HERMES_HOME" -czf "$PRIVATE_BACKUP/hermes-home-before-migration.tar.gz" .`. Set `$PRIVATE_BACKUP` to a private directory outside the profile and check that the archive contains `state.db`, `projects.db`, and `hermes-app/metadata.sqlite`; any plugin attachment directories must be present as well. Restore into an empty *new* isolated `$HERMES_HOME` with `tar -C "$HERMES_HOME" -xzf "$PRIVATE_BACKUP/hermes-home-before-migration.tar.gz"`, then verify all three databases before starting the runner. This is a stopped-profile file-set procedure, not a live SQLite snapshot. P1-05 does not introduce a schema migrator; an incompatible future plugin version requires its own tested migration and rollback gate.
