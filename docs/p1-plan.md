## 1. P1 交付目标

交付一个可在隔离 Hermes profile 中安装、停用和卸载的独立插件，以及最小共享 TypeScript 客户端协议模块与双端测试客户端。客户端协议必须能支撑 Channel/Thread、连续用户历史、可靠发送、断线补齐、执行交互和附件。桌面/手机正式界面与签名安装包属于 P2/P3；不能把测试客户端当正式 App。

最终方向仍是独立桌面和手机 App。优先保留 Hermes 的 Agent、Project、SessionDB、工具和压缩机制，不修改核心或复制修改核心文件。

## 2. 最小架构与职责

- **Hermes App platform plugin**：使用正式平台注册接入 GatewayRunner。单一插件宿主管理 HTTP/WS listener、认证及后台任务；不同时引入第二个聊天服务、Dashboard 宿主和独立执行服务。
- **既有 Hermes 数据**：Project 保存 Channel 对应的项目资料；SessionDB 保存聊天原文和系统头部。已有显示历史/lineage 逻辑继续复用。
- **插件自有元数据**：仅增加稳定 Thread/消息引用、全新会话初始化标记、接收与执行状态、同步游标、已读、附件引用。建议采用插件自有小型 SQLite 元数据库，不修改核心 schema；hosted-rooms 的恢复设计/原语可参考，但不直接套用多人 Discussion 策略。已实测 Discussion 不保证逐消息 FIFO；正文仍唯一存于 SessionDB。
- **共享 TypeScript 模块**：协议类型、连接恢复、消息归并、游标和错误状态。不依赖 DOM、Electron preload 或 React Native UI。
- **桌面/手机**：各自处理界面、系统凭据、通知、文件选择和生命周期。P1 用测试客户端验证同一协议，避免先做漂亮但数据不可靠的 UI。

现有 TUI JSON-RPC 客户端可复用部分代码，但没有正式自定义 method 注册 API 的入口不强行使用。自有插件 HTTP/WS 是已实测替代，不用修改内部 RPC method 表。

## 3. 必须固定的数据语义

### 3.1 Channel、Thread 与 Description

- Channel 对应 Project；Thread 是稳定的用户对话身份，可指向多个压缩续接的物理 Session。
- 只有全新的用户会话在初始化时注入一次 Channel Description；使用正式插件扩展点，不逐条注入。
- 时间/长度压缩、idle compaction、冷恢复和内部 prompt rebuild 均不触发插件补入 Description。压缩产生的物理 successor 仍属原会话，不按新会话处理。沿用 Hermes 自己的上下文，不强制重现 Description 原文，也不主动删除已有内容。
- 修改 Channel Description 默认只影响之后创建的 Thread，是本规划建议；已有 Thread 更新策略待确认，不默默热更新。
- 不混入其他 Thread、branch 或子任务的历史。归档是可逆的内容组织操作，不等于删除历史。

### 3.2 消息与接收

- 每次新发送生成新的 `client_message_id`；同一次发送的网络重试复用该 ID。相同文本的两次独立发送仍是两条消息。
- 服务端返回 `accepted` 必须意味着请求已持久保存且可在崩溃后查询，不以 WebSocket 写入成功或 `_gateway_accepted` 标志替代。
- 输入接收记录仅用于交接与恢复，不能发展成与 SessionDB 竞争的第二份聊天历史；进入权威历史后的引用、保留和清理要有明确规则。
- 消息引用有稳定逻辑 ID，不能直接假设 `messages.id` 在压缩后不变，也不能用正文哈希合并相同内容。若无法确定可靠映射，必须在该任务验收时阻断后续集成。
- 区分接收确认、执行开始、流式草稿、最终持久消息与失败。流式 token 不逐条写成永久同步事件。

### 3.3 执行与恢复

建议状态：`accepted / queued / running / waiting / completed / failed / interrupted / unknown`；可在实现时合并确实无用的状态，但不能把“结果未知”报告为成功或自动重跑。

- 每个 Thread 有一个执行 owner。普通离线不停止执行；停止、超时和资源上限仍生效。
- 运行中普通新消息建议进入显式队列；“追加指令/打断”应为独立操作，不能因为核心 busy/steer 行为而悄悄改变发送语义。
- 重启后可安全恢复尚未开始的持久请求；已经开始且结果未知的执行先核对权威历史及核心状态。
- 不承诺外部工具副作用 exactly-once，不盲目重跑付款、发送、删除等操作。核心 auto-resume 与插件恢复策略必须验证一致，不能各重试一次。
- 最终消息已入库但同步事件未记录时，恢复流程应能补齐通知引用；不得再次生成一条 final 来掩盖窗口。

### 3.4 同步与阅读

- HTTP 读取有界快照/历史，WS 提供在线增量与临时进度；持久事件或可重建变更索引支持断线、缓存淘汰和服务重启。
- 快照返回确定水位；增量从对应水位开始，避免快照与订阅之间漏消息。重复、乱序事件按身份与版本归并。
- 游标失效必须明确返回并触发重新同步，不能返回空数组假装没有变化。
- 同步事件优先保存权威记录引用及版本，不复制全文聊天数据库。后台最终结果同样进入这一链路。
- 已读游标按同一身份与 Thread 单调推进，未读数按可见消息计算，不用控制事件序号差代替。

### 3.5 审批、附件与身份

- 审批绑定具体执行、请求 ID 和运行实例；一次决议，其他端收起。重启后已消失的等待者标记过期，不能把旧批准应用到新的执行。
- 首版建议单 owner 多设备；服务端固定 profile/身份，不能信任客户端自行指定 profile。多人角色权限不纳入默认范围。
- HTTP 和 WS 均验证凭据；停用或撤销后旧连接失效。令牌不出现在 URL、日志、通知正文或安装包常量中。
- 附件持久保存、绑定 Thread、使用不透明引用；服务端校验路径、大小、权限，上传失败可回收。现有一次性浏览器 artifact 接口不能直接当聊天附件。
- 推送仅作提醒；正文同步以服务端权威记录为准。APNs/FCM 账户与真机接入不在 P1 本地实现的默认授权内。

## 4. 实施顺序与验收

### P1-01 插件骨架与接口边界

工作：manifest、正式 platform 注册、单宿主 HTTP/WS、认证、配置及版本能力响应、显式 start/stop、隔离测试环境。

验收：未修改核心；真实 GatewayRunner 加载；未认证及越权拒绝；两个测试客户端连接；停止后 listener/任务释放；禁用不影响原有平台。使用内部 Hermes API 的位置集中、注明基线并有兼容测试，不建设通用兼容框架。

### P1-02 Thread 与连续历史

依赖 P1-01。工作：Project/Thread 映射、初始 Description、压缩 lineage、稳定消息引用、有界历史分页、统一可见投影。

验收：两个同 Channel Thread 共享初始说明但历史隔离；实际压缩/续接/冷恢复后用户聊天原文不丢、不重，插件不再注入 Description；反复同文消息不被错误合并；分页无祖先截断，branch 不混入；内部摘要和 `session_meta` 不进入普通消息。

### P1-03 可靠接收、执行与持久同步

依赖 P1-02。工作：发送重试去重、接收/入队恢复、每 Thread 执行所有权、最终结果索引、持久游标、快照/增量衔接、跨端已读。

验收：分别在“接收已落盘”“执行已开始”“final 已入库但通知未写”处终止隔离进程并重启；重试不重复新执行，结果未知明确可见；双端、长离线、重启、乱序均不漏不重；客户端关闭不取消正常任务。该阶段是 P1 的关键路径，不能用内存队列替代。

### P1-04 交互与内容补齐

依赖 P1-03。工作：在线审批/澄清与过期状态、停止/队列、后台/cron 结果持久投递、附件、搜索与必要清理。

验收：双端竞争答复只生效一次；另一端即时收到状态变化；重启旧审批不再执行；实际隔离 cron fire 的结果进入正确 Thread；附件重启后可读、越权/路径穿越/超限拒绝；删除/归档策略不遗留无主元数据或误删原文。

### P1-05 共享契约与回归交付

依赖 P1-03，可与 P1-04 的独立部分并行。工作：共享 TS 协议模块、桌面与移动目标测试客户端、接口文档、迁移/备份/回退说明、完整自动验收。

验收：同一套协议测试在选定桌面与移动 JS 目标通过；没有 Node/Electron 依赖进入移动公共模块；上述场景可一条命令在隔离 profile 重跑；输出插件包、测试报告、已知限制。正式桌面/手机安装包与真机 UX 进入 P2/P3，不混淆阶段。

## 5. P0 与 P1 的界线

P0 的完成是：每项关键需求已识别现有保证、缺口或外部验证条件，并给出不改核心的候选实现路径及可执行验收；不是将所有产品功能实现到通过。

若收尾验证发现某项硬需求无法通过正式插件和允许的既有接口实现，应列为架构阻塞，不能把“以后再做”当 P0 通过。若只是缺少要在 P1 实现的映射、持久同步与恢复逻辑，应明确归入上面的任务，不继续扩写一次性探针成为生产后端。

## 6. 开工前决策与估算方式

- 首版建议单 owner 多设备；运行中普通发送采用排队，显式追加/停止另外处理。与用户已有要求兼容，但仍需在 P1 开工结论中确认。
- 桌面优先沿用 Electron/React；手机采用 Expo/React Native 原生视图；主控 Metro Android JS 导出及纯协议 5 项测试通过。Flutter 不选为首发路线，因为要重写既有 TS/桌面资产；不是 Flutter 性能较差的判断。手机 JS 导出不等于 APK/真机通过。
- 目标 OS、签名及推送账户属于客户端发布门槛，不要求为 P1 插件测试提前购买或开放生产权限。
- P1 依赖图：01 → 02 → 03 → 04/05 → 集成验收。按单名熟悉本栈的工程师估算有效工作量：01 为 1–2 人日，02 为 2–3 人日，03 为 3–5 人日，04 为 2–4 人日，05 为 1–2 人日，合计 **9–16 人日**。这是工作量假设，不是日历工期或 Agent 运行时承诺；不含 P2/P3 UI、真机、签名、生产部署或上游 native 验证。
- 只有用户明确批准 P1 实现后才创建并启动相应执行卡；本文件不授权生产安装、网关重启、远端推送或发布。

## 7. 推荐开工切片与接口草案

**先做 P1-01/02（估算 3–5 人日）并验收，再放行 03–05。** P0 已复现压缩后顺序/重复差异，因此这不是可略过的文档任务。若无法在 plugin-only 约束内得到稳定原文顺序与身份，不应先做完整 UI 再返工。

建议最小接口，不强行兼容整个 TUI RPC：
- `GET /v1/capabilities`：协议版本及实际支持能力；不暴露所有 Hermes 管理命令。
- Channel/Thread CRUD 与 `GET /v1/threads/{id}/messages?before=...&limit=...`：不透明页游标，固定授权主体。
- `POST /v1/threads/{id}/messages`：`client_message_id`、正文和附件引用；响应包含稳定消息/执行引用和持久接收状态。
- `GET /v1/sync?cursor=...` 与 WS `/v1/events`：共享同一持久水位；事件带 `event_id`、`cursor`、`thread_id`、记录引用和版本。过期游标要求重新取快照，不静默跳过。
- 审批/澄清、停止、已读和附件使用独立受权操作；审批必须带请求与执行代际，不以客户端 UI 状态授权。

第一版只实现任务验收需要的字段，稳定身份/幂等/授权/故障恢复不可省略。接口命名是规划，可在 P1-01 契约评审中收敛，不能据此声称已有路由。

P1-02 特别复验：默认 in-place 与显式 rotation/idle，正常和改变 cwd 的重建均不补 Description，保护首尾消息、重复同文、分页跨段、cold restore。不使用文本哈希“去重”来掩盖重复或顺序问题；同逻辑消息的原始顺序应由稳定元数据与原始记录关系确定。

P1-03 特别复验：真实隔离 SIGKILL 的接收/入队/final-通知窗口，以及核心 auto-resume 和插件恢复不重复接管。不能只布置最终 DB 状态后声称所有崩溃窗口已测。
