# iOS TestFlight build and self-hosted updates

Status: in progress on branch `feat/ios-testflight-updates`. The update service is deployed. The first TestFlight build is not uploaded yet.

## What the user gets

- Hermes App is a real iPhone app, installed from TestFlight. Its bundle ID is `space.tuly.hermesapp`.
- Client changes (JavaScript and assets) reach the installed app without a new TestFlight build. The app checks for an update when it starts. It downloads the update in the background. The update runs at the next cold start. Start-up does not wait for the network, and the app shows no prompt.
- A new TestFlight build is necessary only when native code changes (Expo SDK, a native module, native configuration). The runtime version shows this automatically.
- The Expo Go test entry (`exps://agent.tuly.space`) stays as it is. Expo Go takes the SDK version from `extra.expoClient.sdkVersion` (58.0.0), not from the runtime version.

## Decisions (confirmed by Jamie)

- No EAS. The Mac mini builds and uploads the binary. This host serves updates.
- Update URL: `https://hermes-app-api.tuly.space/mobile-updates/manifest`.
- Bundle ID `space.tuly.hermesapp` for the standalone app. Android keeps `space.tuly.hermesapp.dev` until an Android release is planned.

## Runtime version

- The fingerprint policy hashes native inputs: native packages and versions, autolinking, the native parts of the app config, `package.json` scripts. A change to any of them gives a new runtime version. An update reaches only binaries with the same runtime version, so JavaScript that needs new native code never runs on an old binary.
- `version` and `ios.buildNumber` are not in the fingerprint (measured: buildNumber 1 and 7 gave the same value). A new TestFlight build that changes only the build number keeps the runtime version.
- `apps/mobile/ios/` and `apps/mobile/android/` are generated by `expo prebuild` and gitignored. The fingerprint skips gitignored native folders, so Linux (no `ios/`) and the Mac mini (after prebuild) compute the same value. The build checks this (see Build).

## Code signing of updates

- `npx expo-updates codesigning:generate` made a 2048-bit RSA key and a self-signed certificate, valid until 2036-11-04. The certificate is in the app binary. The app accepts only manifests and directives signed with the private key.
- `publish.mjs` signs at publish time. It refuses to write a record when the signature does not verify with `apps/mobile/certs/certificate.pem`.
- If the private key is lost, installed apps can no longer receive updates. A new TestFlight build with a new certificate is then necessary. Keep a backup of `keys/`.

## Store layout

```
store/assets/<sha256>.<ext>                         immutable, content-addressed
store/releases/<platform>/<runtime>/<time>-<id>.json   every published record
store/current/<platform>/<runtime>.json             the active record
```

A record holds the exact manifest (or directive) text and its `expo-signature` value. The server returns 204 when no record exists, when the client already runs the current update, or when a rollback is active and the client already runs the embedded update.

## Publish an update

Run on this host from the repository that the update must contain (normally `main` after a client release):

```bash
export PATH=/home/hermes/.asdf/installs/nodejs/24.14.1/bin:$PATH
M=/home/hermes/.hermes/profiles/jamie/workspace/hermes-app/mobile-updates
node services/mobile-updates/publish.mjs publish --platform ios \
  --store $M/store --key $M/keys/private-key.pem \
  --base-url https://hermes-app-api.tuly.space/mobile-updates \
  --expect-runtime <runtime of the TestFlight build> --message "<what changed>"
```

`--expect-runtime` stops the publication when the runtime version differs from the installed build (a native change needs a new build first). The output gives the update id, the bundle URL and the size.

## Roll back

- To an earlier update: `publish.mjs rollback --platform ios --runtime <rv> --to <update id>` (ids from `publish.mjs list --platform ios --runtime <rv>`). The client takes an update only when it is newer than the running one, so the tool republishes the old content with a new id and time.
- To the code inside the binary: `publish.mjs rollback --platform ios --runtime <rv> --embedded`. This sends the signed `rollBackToEmbedded` directive.

## Build (Mac mini)

Script: `scripts/ios-macmini-build.sh <build number> <expected runtime>` (copy to `~/hermes-ios-build/build.sh`; logs `build.log`, `archive.log`, `export.log` in `~/hermes-ios-build/`).

Toolchain on the Mac mini: Xcode 27.1, Node `~/.local/node-v24.14.1`, CocoaPods 1.17.0 as `~/.local/bin/pod`. The system Ruby 2.6 is too old for CocoaPods (`ffi` needs Ruby 3.0+), so the wrapper uses Ruby 3.3 from a micromamba env (`~/.local/micromamba/bin/micromamba`, env `~/.local/cocoapods-env`, conda-forge).

1. Copy the source (`git archive` of the commit: `apps/mobile`, `packages/client`, `services`, root files) to `~/hermes-ios-build/src`.
2. The source folder must be a git repository (`git init` is enough). Without git, the fingerprint cannot see that `ios/` is ignored, counts it as native source (`workflow generic`) and gives a different runtime version (measured: `8d4f25a3…` instead of `b32a4b59…`). The script runs `git init` when needed and checks `git check-ignore apps/mobile/ios`.
3. `npm ci` in `apps/mobile`, `npx expo prebuild --platform ios --no-install`, `pod install` in `ios/`.
4. Check that `npx expo-updates runtimeversion:resolve --platform ios` matches the value on this host. The script stops on a mismatch.
5. `xcodebuild archive` (Release, automatic signing, `-allowProvisioningUpdates`), with `CURRENT_PROJECT_VERSION` = the build number.
6. Export with `method app-store-connect`, then upload and check the build in App Store Connect / TestFlight.

Signing: Xcode on the Mac mini has no Apple account (`DVTDeveloperAccountManagerAppleIDLists` is empty), so `-allowProvisioningUpdates` alone fails with "No Accounts". The build uses an App Store Connect team API key with the Admin role (`-authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID`). With that key, Xcode creates the Apple Distribution certificate and the App Store profile, and the same key uploads the build. The `.p8` stays on the Mac mini in a mode-700 folder. It is never printed, copied or committed.

Generated Info.plist (build 1, checked): `CFBundleShortVersionString` 0.1.0, `CFBundleVersion` 1, `ITSAppUsesNonExemptEncryption` false, photo/camera/microphone usage strings from the picker plugins. Expo.plist: `EXUpdatesURL` as above, `EXUpdatesRuntimeVersion` `file:fingerprint`, `EXUpdatesCheckOnLaunch` ALWAYS, `EXUpdatesLaunchWaitMs` 0, code signing metadata keyid `main`.
